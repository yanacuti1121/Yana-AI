CONNECTORS

Signing in with Google
doesn't grant Gmail access.

Yana keeps three concepts distinct: the local Studio profile, an optional sign-in identity, and each service connector — each with its own permission scope and credential, none of them automatically granting another.

Open StudioSee Governance

3 SEPARATE CONCEPTS

Not mixing profile, identity and service permission.

Local Studio profile

Identity for whoever uses this machine. Password hashed with scrypt, stored locally. No Yana account on any server.

local password scrypt hash no server account

Sign-in identity (optional)

Google Sign-in — scope limited to openid profile email. Only verifies identity, carries no service permission.

google:identity scope: openid profile email purpose: authentication

Service connector

Gmail, GitHub, Slack, Notion — each its own OAuth grant, its own scope, its own token, its own revoke.

google:gmail scope: gmail.readonly purpose: integration

THE REAL STATUS OF EACH CONNECTOR

Not glossing over what isn't done.

This site doesn't claim every connector is equally ready. Here's the real status.

Google (identity + Gmail)working, PKCE + loopback callback
GitHubworking via device flow, needs a public client ID
Slacknot yet — needs a trusted token broker
Notionnot yet — needs a trusted token broker

REVOKING THE RIGHT SCOPE

Revoking Gmail doesn't sign you out of Google.

Because google:identity and google:gmail are two independent OAuth grants, revoking one doesn't affect the other — even though both use the same Google provider.

CREDENTIAL STORAGE

No token ever leaves the main process.

Tokens are encrypted via Electron's safeStorage (backed by the OS Keychain), written atomically, with 0600 permissions. The renderer (UI) never receives a real token — only connection status (connected/expired/error).

YANA PRINCIPLE

Every connection has its own permission and credential.

That's not a slogan — it's how IntegrationManager actually stores and revokes each connector, independently of the others.
