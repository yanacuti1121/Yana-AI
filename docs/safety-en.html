SAFETY / GUARDRAILS

Blocked before it asks,
not apologized for after.

From blocking a plain destructive command to a supervisor running outside the AI session with authority to stop the whole project — these are real, active blocking layers, not a list of safety ideas.

See Giám ThịSee Governance

THE BLOCKING LAYERS

From a single command to the whole session.

Destructive command guard

Blocks rm -rf, force-push, pipe-to-shell, drop table before the command runs — not a warning after it already ran.

rm -rf → block git push -f → block curl | bash → block

Blast radius policy

An action touching many files or a sensitive area needs explicit approval before it executes — never runs through silently.

> 50 files in 1 command → needs explicit confirmation

Circuit breaker

A repeatedly failing tool gets temporarily locked out (60s → 300s → 1800s), preventing an infinite retry loop from burning tokens.

CLOSED → OPEN → HALF_OPEN → CLOSED

GIÁM THỊ

A supervisor that runs outside the AI session,
not a hook that ends with it.

An in-chat hook only enforces a shared safety state — the hook itself holds no HALT authority. That authority belongs only to Giám Thị, a process running independently at the OS level, checking periodically and able to lock the entire project when it detects an unreviewed change to a sensitive area.

Periodic tickCPU, RAM, disk, sessions, receipt chain
Anomaly detectedcreates a shared lock file
Every AI sessionrespects the lock immediately
Unlockingneeds actor + reason, recorded first

INFRASTRUCTURE INTEGRITY

Rules and hooks are hash-locked too.

Files under core/rules/, core/hooks/, core/gates/ are pinned by SHA-256 in a dedicated manifest. Editing a file in that zone without updating the manifest — exactly what happened for real during this project's own development — makes Giám Thị HALT at the very next check.

YANA PRINCIPLE

Safety is architecture,
not a promise.

Giám Thị doesn't ask an agent's opinion before it HALTs — that's exactly why it works.
