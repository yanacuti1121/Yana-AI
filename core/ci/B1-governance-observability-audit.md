# B1 — Flaky governance / Nightly orchestration / CI observability / Categorical scorecard audit

Companion to `B1-test-the-tests-audit.md`. Same method: evidence gathered
by reading the actual `.github/workflows/*.yml` files and repo tree, no
implementation added in this pass unless noted.

## Flaky governance

Rule: no "rerun until green"; track module/owner/frequency/root
cause/severity/tracking entry per flaky test.

- **Rerun-until-green check: CLEAN.** `grep -rniE "retry|rerun|continue-on-error"
  .github/workflows/*.yml` finds a single hit, and it's this workstream's
  own comment in `release.yml` explicitly *rejecting* `continue-on-error`
  as a way to hide failures — not a retry mechanism. No workflow in this
  repo reruns a failed job/step to make it pass.
- **Tracking registry: GAP.** No file, workflow annotation, or doc
  currently records module/owner/frequency/root-cause/severity for any
  test that has ever flaked. There is nothing to point to as "the flaky
  tracker" because it doesn't exist yet.

## Nightly/adversarial orchestration

Rule: a scheduled tier may run race-test repeats, soak/resource tests,
service lifecycle cycles, malformed-provider matrices, state-corruption
recovery, full platform suites, dependency/security scans; failures
should retain useful artifacts.

- **Scheduled workflow: GAP.** `grep -l "schedule:" .github/workflows/*.yml`
  returns nothing — there is no nightly or periodically-scheduled
  workflow in this repo at all. Every existing workflow triggers on
  push/PR/tag/release only.
- This item overlaps the program document's own B4 section ("T5
  NIGHTLY/SOAK" execution tier), which is where this gets designed as
  part of the 5-tier execution matrix rather than bolted on ad hoc here.
  Recording the gap in B1 per the document's own structure; the actual
  workflow gets built when B4 is reached, so the tier design and the
  implementation aren't done twice.

## CI observability

Rule: artifacts should explain what grew, when, which process/thread,
which phase; no secret-containing artifacts.

- **Audit-report artifacts: present, unconditional.** `ci.yml` and
  `yana-audit.yml` both upload their self-audit reports with
  `if: always()` — these survive success and failure alike. Checked for
  secret risk: both upload markdown/SARIF audit reports generated by this
  repo's own audit tooling, not raw environment dumps or logs, so the
  existing "no secret-containing artifacts" bar is met by what's there.
- **Test-failure diagnostics: GAP.** The `rust-tests` job (and other
  test-running jobs) has no `if: failure()` step capturing test output,
  thread dumps, or resource usage beyond whatever appears in the raw
  step log. For a race-condition regression (several of which are named
  in the "Test-the-tests" targets above) a bare pass/fail in the log
  gives no answer to "what grew, when, which thread, which phase" if it
  fails intermittently in CI but not locally.

## Categorical scorecard

Rule: never a fake numeric safety score; truthful categorical status per
subsystem/platform instead.

- **Existing state: CLEAN.** Searched this repo's CI-facing docs/scripts
  (`core/ci/`, workflow files) for `safety_score`/`trust_score`-style
  numeric patterns; the only hit is this audit's own sentence describing
  the rule, not an actual score being emitted. Nothing in the current CI
  surface produces a fabricated numeric safety percentage.
- Note: `.claude/rules/` and `core/rules/` do define a session-level
  "trust score" concept (`00-meta-rule-enforcer.md` and related hook
  scripts) — that's a distinct, already-scoped mechanism for agent
  session behavior, not a CI/test-subsystem safety score, and is out of
  this audit's scope.
- This B9 closure report (once reached) must use categorical status
  (STABLE FOR CURRENT SCOPE / STABLE WITH EXPLICIT DEBT / REQUIRES
  FURTHER STABILIZATION) per subsystem, matching what this section
  requires — not a numeric rollup.
